# ТЕХНИЧЕСКОЕ ЗАДАНИЕ НА MVP — ПРОМТ ДЛЯ ИНЖЕНЕРА

Статус: v1.1 от 2026-10-17. Числа, помеченные `[КАЛИБРУЕТСЯ]`, ещё уточняются
балансом — структуру кодить можно, значения выносить в конфиг, не хардкодить.

---

## 0. ЧТО СТРОИМ

MMO-стратегия на карте реального мира. Поверхность Земли разбита на гексагональные
ячейки («пиксели»). Игрок ставит **одну** базу, она автоматически захватывает
окружающие пиксели **внутри углового сектора**, ширина которого зависит от уровня
базы. Захваченные пиксели дают энергию, энергия идёт на апгрейд базы, апгрейд даёт
шире сектор и быстрее захват. Когда территории двух игроков соприкасаются —
пограничная война, границу двигает тот, кто сильнее.

**Цель MVP: 10 000 игроков комфортной игры.** Это проектная цель, не потолок.

**Главное, что нужно понять до начала работы:** нагрузка этой игры определяется
не числом игроков онлайн (пик ~250 человек при 10k MAU), а числом непрерывно
растущих территорий (10 000 всегда). Поэтому ключевое архитектурное решение —
раздел 4. Прочитай его первым.

## 1. АККАУНТЫ

- Авторизация: **Google OAuth** и **Telegram Login Widget**. Больше ничего в MVP.
- Одна регистрация = один игрок = одна база.
- Привязка обязательна до постановки базы.
- `NEW_ACCOUNT_CRYSTAL_DELAY = 72 ч` — премиальная валюта за ежедневные задания
  начисляется начиная с 4-го дня (анти-ботоферма).
- Device attestation (Play Integrity / App Attest) — требуется для начисления
  ежедневных заданий, если будет мобильный клиент. Для веба — fingerprint.
- `SAME_FINGERPRINT_MIN_DISTANCE` и `BASE_PLACEMENT_COOLDOWN_PER_FINGERPRINT`
  `[КАЛИБРУЕТСЯ]`.

Премиальная валюта **непередаваема между игроками. Рынка игроков нет.** Это не
фича, это несущая мера против RMT — не закладывай API, который позже можно
превратить в передачу.

## 2. МОДЕЛЬ МИРА

| Параметр | Значение |
|---|---|
| Сетка | **H3 (Uber), resolution 8** |
| Площадь ячейки | 0,7373 км² (ребро ~461 м, поперечник ~920 м) |
| Играбельно | Суша без Антарктиды = **183,0 млн ячеек** |
| Океан | Не захватывается и не застраивается в MVP |
| Политические границы | **Не рисуем и не храним.** Только рельеф, вода, города как точки интереса |

Почему H3, а не quadkey/S2: площадь ячейки не «плывёт» по широте (разброс ±8%
против 400% у Web Mercator), ровно 6 соседей и единая метрика расстояния — радиус
считается в гекс-кольцах, без вопроса «диагональ это 1 или 1,41». Это напрямую
входит в формулы ниже, так что замена сетки = переписывание всей математики.

Полезные тождества гекс-сетки (используются везде):
```
пикселей в кольце d        = 6d
пикселей в диске радиуса D = 1 + 3D(D+1) ≈ 3D²
периметр блоба из P px     = 6·√(P/3)
```

Иерархия: res 8 → родитель res 5 содержит 7³ = **343** ребёнка. 343 бита = 44 байта.
Это основа упаковки данных (раздел 5).

Статика terrain: агрегировать ESA WorldCover + GHSL population grid в H3 res 8
**оффлайн, один раз**, упаковать по 4 бита на ячейку, положить в CDN. Это
read-only данные, в рантайме не меняются.

| Terrain | Множитель добычи |
|---|---|
| Urban / built-up | 1,60 |
| Cropland | 1,20 |
| Grassland | 1,05 |
| Forest | 1,00 |
| Shrub / tundra | 0,75 |
| Mountain (slope >25°) | 0,70 |
| Desert / bare / ice | 0,40 |
| Coastal (1 кольцо от воды) | +0,15 аддитивно |

## 3. ЯДРОВАЯ МЕХАНИКА: СЕКТОРНЫЙ ЗАХВАТ

База имеет **уровень 1…30**, **азимут** (направление сектора) и **угол**, зависящий
от уровня. Захват идёт только внутри сектора.

```
// УГОЛ
φ(L)        = 0.10 + 0.90 * ((L-1)/29)^0.40        // доля полного круга   [КАЛИБРУЕТСЯ: экспонента]
ANGLE(L)    = 360 * φ(L)                            // градусы
             φ(1) = 0.10 → 36°      φ(30) = 1.00 → 360°

// СКОРОСТЬ ЗАХВАТА (не зависит от угла)
R(L)        = R_BASE * CAPTURE_GROWTH^(L-1)                           [КАЛИБРУЕТСЯ]

// ПОТОЛОК ТЕРРИТОРИИ — угол ограничивает РАЗМЕР
P_CAP(L)    = P_CAP_DISK(L) * φ(L)
P_CAP_DISK(L) = P_CAP_DISK_BASE * CAPTURE_GROWTH^(L-1)                [КАЛИБРУЕТСЯ]

// ХАРАКТЕРНОЕ ВРЕМЯ — выпадает из геометрии, НЕ отдельная константа
τ(L)        = P_CAP(L) / R(L) = 30ч * φ(L)
             τ(1) ≈ 3 ч   →   τ(30) = 30 ч

// РОСТ ТЕРРИТОРИИ — замкнутая форма, это критично для раздела 4
P(t)        = P_CAP(L) - (P_CAP(L) - P₀) * exp(-(t - t₀) / τ(L))
R_eff(P,L)  = R(L) * max(0, 1 - P / P_CAP(L))
```

`τ(L) = 30·φ(L)` означает, что циклы экспансии естественно короткие в онбординге
(~3 часа на L1) и длинные на эндгейме (~30 часов на L30). Это сделано осознанно —
не «исправляй» это, добавляя отдельный таймер.

**Радиус сектора:** `D(L) = √(P_CAP(L) / (3·φ(L)))` гекс-колец. При узком секторе
та же территория лежит дальше от базы — это влияет на upkeep и на проекцию силы.

**Азимут.** Выбирается при постановке базы. Поворот — платный, с кулдауном,
`[КАЛИБРУЕТСЯ]`. Важно для реализации: сектор, упирающийся в океан или в чужую
территорию, **не теряет ход роста, а перенаправляет его внутри доступного угла** —
иначе игрок на берегу наказан географией.

**Порядок захвата детерминирован:** спиральный обход колец внутри сектора, tie-break
по `hash(h3_index XOR base_seed)`. Это обязательное требование — из него следует,
что любой сервер восстанавливает точный набор принадлежащих игроку пикселей из
пяти чисел `(base_cell, L, azimuth, P, t_last)`. Не делай захват случайным.

## 4. АРХИТЕКТУРА: НЕ ТИКИ, А ЛЕНИВОЕ ВЫЧИСЛЕНИЕ

**Это самое важное решение в проекте. Тиковая симуляция здесь — архитектурная ошибка.**

| | Тики | **Ленивое вычисление** |
|---|---|---|
| Фоновый CPU | 10 000 игроков × 1 Гц вечно, даже при нуле онлайна | **0** |
| Запись в БД | постоянный поток событий захвата | чекпоинт раз в 10 мин / на выходе из сессии |
| Состояние мира | гигабайты на диске, кэш-мисс на каждый запрос | **десятки МБ в памяти** |
| При росте аудитории ×3 | переписывать | линейно по памяти |

Как считать:

**(1) Территория — чистая формула.** Одна экспонента на запрос, формула в разделе 3.
Никаких итераций.

**(2) Энергия — интеграл с таблицей поиска.** Интеграл `∫(x − x^2.5)dt` при
экспоненциальном `P(t)` не берётся в элементарных функциях. Решение: предпосчитать
таблицу `G[512]` для `G(x) = x − x^2.5` на `[0; 1.6]`, интегрировать шагами по
15 минут с линейной интерполяцией. Окно интегрирования ограничено складом —
максимум ~504 шага. Стоимость одного запроса состояния игрока: **≈3 мкс**,
погрешность против точного численного интегрирования **<0,4%**.

**(3) Конкретные h3-индексы материализуются только по требованию:**
- клиент смотрит на регион карты → материализовать затронутые res-5 тайлы;
- идёт пограничный конфликт → материализовать только кольцо контакта;
- чекпоинт раз в 10 минут.

Между этими событиями **конкретные пиксели не существуют нигде** — существует
только `(base_cell, L, azimuth, P, t_last, seed)`. Прими это как инвариант: любой
код, которому нужен «список всех моих пикселей» в горячем пути, — ошибка проектирования.

**(4) Что действительно требует реального времени:** активные пограничные бои
(пересчёт соотношения сил при изменении сил), триггеры щитов, таймеры стройки.
При 10k игроков это порядка сотни операций в секунду. Тривиально.

**(5) Время только серверное.** `SERVER_AUTHORITATIVE_TIME_ONLY = true`. Клиент
никогда не сообщает, сколько прошло времени.

## 5. ДАННЫЕ

```
// Горячее состояние игрока — то, что реально живёт
player {
  id, auth_provider, auth_subject,
  base_cell          h3 res 8 (int64),
  level              int8  (1..30),
  azimuth            int16 (градусы),
  pixels_held        int32,   // P
  t_last             int64,   // когда P был зафиксирован
  seed               int32,   // детерминизм порядка захвата
  energy, energy_t_last,
  crystals,
  shield_until, upgrade_started_at, upgrade_target_level
}
```

Территория **не хранится построчно.** Варианты по возрастанию предпочтительности:

- ❌ Строка на пиксель — десятки миллионов строк, убивает каждый тайловый запрос.
- ✅ **Упаковка в res-5 тайлы:** `(parent_h3 int64, owner int32, child_bitmask 343 бита)`
  = 56 байт на тайл. На ~2 порядка меньше строк.
- ✅ **Горячее состояние в памяти:** roaring bitmap на игрока. Всё игровое состояние
  мира влезает в один инстанс.

Отдельно построчно учитываются **только спорные пиксели границ** (кто сколько
времени давит) — это малая доля от общего числа.

Шардирование: по крупному H3-родителю, непрерывными кластерами. Cross-shard
протокол нужен только для боёв на стыке шардов — доли процента фронтов.
Конкретный уровень родителя — твоё решение, но заложи его параметром.

## 6. ЭКОНОМИКА

```
// ДОБЫЧА И ПОДДЕРЖАНИЕ
e_px        = 0.5                            // энергии/час с пикселя
M(L)        = 1 + 0.10 * (L - 1)             // множитель от уровня
x           = P / P_CAP(L)

GROSS(P,L)  = e_px * M(L) * P * terrain_avg * FRONTIER_BONUS * ALLIANCE_BONUS * ISOLATION_MOD
UPKEEP(P,L) = e_px * M(L) * P_CAP(L) * x^UPKEEP_BETA
NET(P,L)    = GROSS - UPKEEP

UPKEEP_BETA = 2.5
```

**Это механизм против снежного кома, и он несущий.** Следствия, которые надо знать:

- Максимум чистого дохода — при **x = 0,5429**, и там предельная ценность
  следующего пикселя **ровно ноль**.
- `0,5429 = 1,165⁻⁴`, то есть **оптимально держать столько, сколько было твоим
  потолком 4 уровня назад**. (Тождество верно при CAPTURE_GROWTH = 1,165; если
  калибровка изменит это значение, тождество поедет — пересчитать.)
- При x = 1 доход ровно равен расходу. Выше — игрок разоряется.
- Поэтому расти выгодно **уровнем, а не землёй**.

**Критично для реализации:** upkeep списывается **тем же интегралом, что и доход,
непрерывно по фактической траектории P(s)** — не тиком. Иначе появляется эксплойт:
набрать территорию, собрать добычу, сбросить до оптимума за секунду до тика и не
заплатить суперлинейный штраф. Это удваивает доход и ломает всю кривую прогрессии.
Поскольку энергия и так считается интегралом (раздел 4), эксплойт закрывается
архитектурой бесплатно. Плюс: `ABANDON_COOLDOWN_HOURS = 6`,
`ABANDON_NEUTRAL_LOCK_HOURS = 12`, `ABANDON_DAILY_LIMIT = 0.15 * P`.

```
// АПГРЕЙД
UPGRADE_COST(L→L+1) = 50 * 1.50^(L-1)                      // энергии   [КАЛИБРУЕТСЯ]
UPGRADE_TIME(L→L+1) = min(10 * 1.27^(L-1), 7200)           // минут
UPGRADE_QUEUE_SLOTS = 1 (F2P) / 2 (VIP)
```

Апгрейд — **стройпроект, а не единовременная покупка**: энергия вкладывается
порциями в любое время, таймер стартует при 100%. Обязательно — иначе стоимость
поздних уровней физически не влезает в склад.

```
// СКЛАД
STORAGE(L)     = 14 ч * NET_opt(L)
OVERFLOW_RATE  = 0.25        // выше cap копится на 25% скорости
HARD_CEILING   = 3 * STORAGE(L)
```

14 часов — retention-крючок: ночной сон склад не переполняет, один заход в сутки
теряет часть дохода, но не всю.

```
// БОЕВАЯ СИЛА
POWER(L,P,tech) = 1.20^(L-1) * P^0.75 * (1 + tech_bonus) * ALLIANCE_POWER_MOD
```

Экспонента 0,75 на территории — удвоение земли даёт лишь 1,68× силы, а уровень
даёт 1,20× за шаг. Левелинг доминирует над «нахватать».

```
// ПРОЕКЦИЯ СИЛЫ — падает с расстоянием от своей базы
D_PROJ(L)   = 1.5 * √(P_CAP(L)/3)
Proj(d, L)  = 2^(-d / D_PROJ(L))
```

**Пограничный конфликт — формулы `[КАЛИБРУЕТСЯ ЦЕЛИКОМ]`.** Структура такая:
соотношение сил на конкретном участке границы с учётом проекции и бонуса обороны →
доля скорости захвата, применяемая к врагу → поток отъёма, ограниченный длиной
контакта. Два ограничителя обязательны: порог «насколько сильнее надо быть» и
лимит по длине контакта (иначе можно «проткнуть» врага через один пиксель границы
и выпить всю территорию). Кодируй структуру и выноси все коэффициенты в конфиг —
значения пересчитываются.

```
// ВАЛЮТА
SKIP_COST(t_hours) = max(1, ceil(14 * t_hours^0.90))       // таймер → кристаллы
ENERGY_PER_CRYSTAL(L) = 0.1 * NET_opt(L)
ENERGY_DAILY_CAP_HOURS = 16          // не более 16 часов дохода в сутки за кристаллы
F2P_CRYSTALS_PER_DAY = 40
```

`ENERGY_DAILY_CAP_HOURS` — главный предохранитель от pay-to-win. Без него
покупается максимальный уровень за два дня. Не делай его конфигурируемым «для
удобства тестов» так, чтобы он мог уехать в прод отключённым.

## 7. СИНХРОНИЗАЦИЯ С КЛИЕНТОМ

**Версионирование тайлов, а не push по пикселю.** Клиент опрашивает видимые res-5
тайлы раз в 5 секунд и получает `(tile_version, diff_bitmask)`. Эндпоинт
CDN-кэшируемый. Персональный WebSocket-push по каждому захваченному пикселю даёт
фанаут O(наблюдателей) и не нужен.

WebSocket оставить только для: активных боёв, таймеров стройки, уведомлений.

**Анимация захвата — чисто клиентская косметика.** Сервер не знает ни об одном
юните, дроне или летающем звере: он знает только, какая ячейка кому принадлежит и
когда сменила владельца. Клиент восстанавливает анимацию из этих двух фактов и
рисует юнитов **только внутри видимой области экрана**. Это надо заложить сразу —
переделывать потом больно.

Фракций в игре 5 (разные визуальные подачи захвата + смещение по одной
характеристике в пределах ±15%). Для бэкенда фракция — это `enum` + набор
множителей из конфига, ничего больше.

## 8. ЧЕГО В MVP НЕТ

Не проектируй под это сейчас, но и не закрывай дорогу:

- Океан как играбельная территория (планируется позже, через проекцию силы через воду).
- Вторая база у одного игрока (лицензия существует как SKU, но в MVP не включаем).
- Передача ресурсов между игроками — **никогда**.
- Сезонный сброс карты — нужен будет к месяцу 20–24, заложи версионирование
  состояния мира так, чтобы сброс был возможен.

## 9. ОТКРЫТЫЕ ВОПРОСЫ — ОБСУДИТЬ ДО КОДА

1. **Плотность игроков.** При 10 000 игроков на всю сушу соседи оказываются слишком
   далеко друг от друга и война как контент не происходит. Решается ограничением
   играбельной зоны в MVP и/или принудительно кластеризованным размещением новых
   баз рядом с существующими. Решение влияет на шардирование — нужно до архитектуры.
2. **Онбординг.** На L1 сектор 36° даёт очень маленькую территорию. Константы
   `R_BASE` и `P_CAP_DISK_BASE` пересчитываются под требование «первые 5 уровней
   проходятся в первой сессии». До этого не фиксируй числа в коде.
3. **Платформа: веб или мобильные сторы.** Влияет и на технику, и на экономику
   (комиссия 30% против 3–5%). Решение заказчика, но скажи, что это меняет для тебя.
4. **Формулы боя** приедут отдельно после перебалансировки.
